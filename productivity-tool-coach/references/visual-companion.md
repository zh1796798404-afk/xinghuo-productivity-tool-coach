# 视觉辅助方案规则

## 何时触发

只有在“看方案比读描述更容易做决定”时，才建议视觉辅助。

适合：

- 界面布局
- 页面和组件结构
- 多步骤交互流程
- 表格、报告和文档版式
- 工作流、业务流程和系统架构
- 自动化工具的输入输出
- skill或脚本的操作路径
- 视觉风格和信息层级

不适合：

- 用户已经有明确设计稿
- 只是简单的命令行参数
- 设计选择不会影响第一版
- 用户明确要求直接制作

## 询问用户

不要在开场就询问视觉辅助。先完成足够的需求梳理，确认确实存在多个合理方向后再问：

```markdown
接下来有一个部分，用看实际方案会比读文字更容易判断。

我可以先为你准备2到3个不同方向的视觉辅助方案，
让你直接比较它们的结构、流程、布局或最终效果。

请选择：

A. 先看视觉方案
B. 不需要视觉方案，直接按当前方案继续。

默认推荐：如果当前方向还不明确，推荐A；如果用户已有明确设计或工具非常简单，推荐B。

推荐原因：视觉对照可以在正式制作前发现方向偏差，减少后续返工。

如果以上选项都不符合，可以直接输入你自己的想法。
```

## 方案数量

提供2到3个方案，不固定为A/B：

- 2个方案：决策比较简单，存在两个主要路线。
- 3个方案：需要展示明显不同的取舍。
- 超过3个方案：合并相近方案，避免选择疲劳。

## 方案差异

每个方案解决同一个问题，核心功能范围保持大致相同，只改变一个主要设计维度，例如：

- 单页面 vs 分步骤
- 简洁流程 vs 工作台
- 自动执行 vs 预览确认
- 线性流程 vs 状态看板
- 表格优先 vs 摘要和趋势优先

不要同时改变功能、目标用户、数据模型和视觉风格，否则用户无法判断选择结果。

## 方案说明格式

```markdown
## 方向一：简洁快速型

特点：
- ...

优点：
- ...

取舍：
- ...

## 方向二：工作台型

特点：
- ...

优点：
- ...

取舍：
- ...

默认推荐：方向一

推荐原因：...
```

## 用户反馈

用户可以：

- 选择一个方向
- 选择一个方向并提出修改
- 组合多个方向
- 要求重新提出方案
- 表示全部不合适并自由描述

处理例子：

```text
用户：方向一的结构不错，但我想保留方向二的结果展示。

记录：
- 使用方向一的整体流程
- 使用方向二的结果展示
```

## 原型边界

视觉辅助不是正式制作。只做足够帮助用户判断方向的内容：

- 关键页面或关键步骤
- 代表性输入和输出
- 核心交互
- 必要的状态和反馈

不要在用户选定方向前完成完整后端、复杂数据接入或所有边缘功能。

优先使用当前环境中可用的浏览器、可视化或原型工具。如果没有合适能力，使用轻量的静态预览、截图、流程图或示例输出代替。

## 确认后的处理

用户选定方向后，更新制作方案中的：

- 视觉方向
- 页面或流程结构
- 核心交互
- 第一版范围
- 验收标准

视觉方向确认不等于正式制作确认。仍然要展示更新后的最终制作方案，并等待用户明确回复“确认方案，开始制作”。
