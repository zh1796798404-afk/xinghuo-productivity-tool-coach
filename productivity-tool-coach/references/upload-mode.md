# 上传模式（存量工具回流）

## 定位

教练插件是一体化双模式：**制作模式**负责"从痛点到工具"，**上传模式**负责"从工具到市场"。上传模式服务已经有现成工具的共建者：自动解析工具目录与文档，结构化生成上传表全部字段，用户一屏确认后上传回星火平台。

## 进入方式

- 开场第一屏用户回复 **B**；或跳过选择直接表达"上传 / 分享现成工具"意图；或直接拖入一个**完整的工具目录 / 压缩包**（而非样例数据文件）。
- 进入后发第二屏 B（唯一出处）：

```markdown
📤 好的！把要上传的**工具文件夹或压缩包**直接拖进来。

顺手用一句话说说它是干什么的更好（可选）——我会自动解析出上架信息给你确认，全程不运行你的代码。
```

- 制作模式完成后的"是否分享"确认（见 platform-sync.md）本质是上传模式的另一个入口，字段直接来自草稿，不走本文件的解析步骤。

## 硬前提

上传模式依赖平台配置（`~/.spark-coach/config.json` + lark-cli，见 platform-sync.md）。未配置时明确告知："上传能力需要先完成平台配置（找平台管理员要配置文件），配置好随时再来"——不要尝试绕过。

## 第 1 步：自动解析（只读，绝不运行代码）

读取工具目录内的 README、SKILL.md、入口文件、manifest / package 描述、注释头等**文本内容**，推断生成工具表字段：

| 字段 | 解析来源 |
| --- | --- |
| 工具名称 | README 标题 / 目录名 / manifest name |
| 工具类型 | 按枚举归类：Skill / 脚本 / 网页应用 / 桌面程序 / 表格模板 / 其他 |
| 工具描述 | README 简介 / 代码注释头；解决什么痛点、适用场景 |
| 使用方法 | README 用法节，整理成"第一步/第二步"分步格式 |
| 标签 | 从功能推断业务场景标签，逗号分隔 |
| 运行环境要求 | 依赖声明 / 入口类型；零依赖就写零依赖，需要 agent 环境要注明 |
| 简介图 | 目录内已有截图则用；没有则标"暂无（可选补充）"，不强求 |

解析不到的字段标 `[待补充]`，交给用户在确认卡里填。

**安全与隐私检查（解析同时做）**：

- 扫描疑似敏感内容：`.env`、`secret`、`key`、`token`、`password` 类文件与硬编码凭证——发现即暂停，提醒用户剔除后再继续。
- 包内如混有业务数据文件（真实客户数据、内部报表），提醒剔除；样例数据需脱敏。
- 只读取文本做解析，**不执行、不安装**工具的任何代码。

## 第 2 步：一屏确认卡（一次确认，不逐字段追问）

```markdown
📋 我已解析你的工具，请确认以下上架信息（直接改任何一项，或回复"没问题，上传"）：

- 🏷 工具名称：…
- 📦 工具类型：…
- 📝 工具描述：…
- 📖 使用方法：第一步：…；第二步：…
- 🔖 标签：…
- ⚙️ 运行环境要求：…
- 🖼 简介图：…／暂无（可选补充）

*上传后进入平台审核队列，通过后出现在工具市场，署名是你。*
```

用户修改 → 更新对应字段再展示一次差异；用户确认 → 进入上传。

## 第 3 步：上传与登记

复用 platform-sync.md 的已验证命令，仅两处不同：

- `来源渠道` 写 `存量工具插件上传`（不是"教练制作回流"）。
- 不写 `关联制作记录ID`，也**不创建** build_session 记录（那张表只记录造工具过程）。

流程：打包 zip（剔除敏感 / 数据文件）→ `curl -F "file=@…"` 上传取 `url` → tool 表 `+record-upsert` 登记（审核状态=待审核）→ 告知用户：

```markdown
✅ **已上传星火平台**（审核通过后出现在工具市场，审核结果会通知你）
🔗 下载直链：<url>
```

## 失败与边界

- 上传或登记失败：一句话告知 + 保留本地 zip 路径 + 稍后可重试。
- 解析置信度低（目录里几乎没有可读文档）：不硬猜，确认卡里多留 `[待补充]`，请用户补最关键的名称和描述两项即可。
- 审核驳回后的二次上传：当前 MVP 未接驳回原因回传，用户可带着修改后的工具再次走上传模式（登记新记录时沿用原工具名称，描述中注明"二次提交"）。
