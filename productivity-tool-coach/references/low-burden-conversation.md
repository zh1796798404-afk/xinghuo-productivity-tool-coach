# 低负担对话规则

## 目标

让用户感觉自己只是在回答眼前的一个小问题，而方案草稿在旁边自己长大。不做需求问卷，不为覆盖所有字段延长对话；用户的每次回答都要立刻变成草稿上看得见的变化。

## 聊天输出视觉规范

所有发给用户的消息遵循以下规范，让长内容一眼可扫：

**emoji 语义表**（固定映射，同一含义只用同一个 emoji，不随机加）：

| emoji | 含义 | 用在 |
| --- | --- | --- |
| 👋 | 开场问候 | 开场白首行 |
| 🔥 | 关键行动号召 | 开场的核心问句 |
| ✍️ | 提问 | 每个问题的标题行 |
| 💡 | 默认推荐与理由 | 推荐行 |
| ⭐ | 推荐选项标记 | 推荐选项行尾 |
| 📝 | 草稿更新 | 每答写回的反馈行 |
| 📊 | 进度小结 | 记分板小结首行 |
| 📎 | 附件邀请 | 请求资料时 |
| 🎯 📥 📤 🧩 ✅ | 目标 / 输入 / 输出 / 范围 / 验收 | 草稿预览的字段标记 |
| ✅ ⏳ ❌ | 已清晰 / 部分 / 缺失（或 通过 / 部分 / 未通过） | 记分板与验收核对 |
| 🔍 🎨 | GitHub 检索 / 视觉方案 | 对应环节的提示首行 |
| 🎉 | 定稿 / 完成 | 确认门与交付首行 |
| 🔁 | 迭代 | 再次调用提示首行 |

**排版规则**：

1. 关键问句和关键指令**加粗**；一条消息只保留一个视觉焦点。
2. emoji 只做行首结构标记，不撒在正文句子里；每条消息一般不超过 5 个（草稿预览、记分板的字段标记除外）。
3. 选项每项单独一行，写成 `- **A.** 选项内容`；推荐项行尾加 `　⭐ 推荐`。
4. 超过三段的消息用 `---` 分隔区块；草稿展示后紧接提问时，必须用 `---` 分开。
5. 草稿预览用引用块（`>`）；`[待确认]` 和 `（假设）` 用行内代码包裹，让它们视觉上跳出来。
6. 进度写成 `7/9` 并配文字进度条 `▓▓▓▓▓▓▓░░`。
7. 表格只用于验收核对、GitHub 检索结果等真正的行列数据，不用于普通叙述。
8. 有原生提问/选项控件的环境，选项交给控件呈现，正文保留问题、推荐和理由。

## 低门槛开场

开场白全文只有一份出处：[intake-and-attachments.md](intake-and-attachments.md)。首次回应前先读它，原样使用，不即兴改写。

用户可以从以下任一方式开始：

- 只描述痛点。
- 描述痛点和希望结果。
- 描述已经想到的工具。
- 上传一份最小的脱敏样例。
- 回复"我还不清楚，帮我一起找方向"。

## 复述 + 真实事例锚定（合并一轮，不计问题数）

收到初始描述后，先判断它是否已包含"具体过程"（输入、步骤、输出中至少两项）。

**情况一：描述已经很完整** —— 不再邀请事例，先给正反馈，直接进入草稿：

```markdown
我先按下面的方式理解：

- 🎯 痛点场景：…
- ✨ 想改善的结果：…
- 🧭 初步候选方向：…（只是候选，不定死）

✨ **你描述得很完整**——输入、输出和过程我都有了，后面的问题会少很多。
理解有偏差直接改任何一项；没问题的话，我马上给你搭方案草稿。
```

**情况二：描述较简短** —— 复述与事例邀请合并为一轮：

```markdown
我先按下面的方式理解：

- 🎯 痛点场景：…
- ✨ 想改善的结果：…
- 🧭 初步候选方向：…（只是候选，不定死）

理解有偏差的话，直接改任何一项。

---

如果基本正确，请给我讲讲**最近一次**做这件事的实际经过：

> 你从哪里拿到什么？中间做了哪几步？最后交出什么？大概花了多久？

📎 讲的过程中想起有现成的文件——当时的输入、做完的结果、截图——直接拖进来最好。
```

候选方向可以用任务结构描述（"检索+筛选+汇总""批量输入+统一处理+导出""表单填写+自动生成"），避免过早决定技术方案。

从事例中提取：输入及格式、操作步骤、输出及去向、耗时、出错点、发生频率。这些直接写入草稿，不再单独提问。

退化路径：用户讲不出具体事例时，不追问第二次，改用 [question-framework.md](question-framework.md) 的常规问题推进，相关维度标（假设）。

初始描述不足以形成候选目标时，只追问一个最关键的问题（例如："这项工作完成后，你最希望拿到什么结果？"），不同时要求补齐多个字段。

## 单轮问题规则

每轮只推进一个决定：

1. 按 question-framework.md 的选题算法选出唯一问题。
2. 标题行标注序号和草稿落点：`✍️ **第 3 问 · 填「输出」一栏**`
3. 根据用户上下文生成 2~3 个选项，每项一行，推荐项放第一位并在行尾标 `　⭐ 推荐`。
4. `💡 **推荐 X**：一句话理由`
5. 末尾固定写（斜体）：`*如果以上选项都不符合，可以直接输入你自己的想法。*`
6. 有原生提问/选项控件的环境优先用控件（内容等价）。

## 低负担回答入口

在用户可能不确定的决策上，可以额外提供：

- `按推荐继续`
- `我不确定，你来决定`
- `暂时跳过`
- `先给我一个初版方案`

这些不是新的必答选项。用户可以用自然语言回答，也可以修改、组合或拒绝预设选项。

## 每答写回反馈

每收到一个回答，按 [draft-plan.md](draft-plan.md) 写回草稿后，聊天内只给一行反馈：

```text
📝 已更新草稿：输出 → Excel 表格（含失败清单）　·　还剩 2 个 [待确认]
```

不重贴草稿全文，不复述用户刚说的话。

## 不知道时的处理

用户说"不知道""都可以""随便""你决定"时：说明影响 → 默认方案写回草稿标（假设）→ 允许回复"按推荐继续" → 不阻塞第一版就推进下一题。示例：

```markdown
这个决定主要影响第一版的操作复杂度。你暂时没有偏好，我先按"单人使用、最少配置、先跑通一个完整闭环"写进草稿（标为假设）。

---

✍️ **第 4 问 · 填「输出」一栏**

你希望工具最后输出表格，还是可直接发布的内容？

- **A.** 表格　⭐ 推荐
- **B.** 可直接发布的内容

💡 **推荐 A**：先保留结构化数据，更容易检查结果和后续扩展。

*如果以上选项都不符合，可以直接输入你自己的想法。*
```

## 记分板小结

触发：答满 3 个计数问题后，或覆盖度达到 7/9 时（问题上限只有 5，整个流程通常最多出现一次）。

```markdown
📊 **草稿进度：7/9 项已清晰**　`▓▓▓▓▓▓▓░░`

- ✅ 目标 · 使用者 · 现状 · 输入 · 输出 · 操作流程 · 第一版范围
- ⏳ 约束——还差一项：结果要不要发给同事
- ❌ 验收标准

---

**接下来怎么走？**

- **A.** 现在直接出正式方案　⭐ 推荐——剩下的我用默认值补上，标为假设
- **B.** 把剩下两项问完（还需约 2 个问题）

💡 **推荐 A**：核心九项已清晰七项，先看完整方案比继续答题更容易发现偏差。

*如果以上选项都不符合，可以直接输入你自己的想法。*
```

小结不重新复述完整对话，也不为了展示进度额外提问。

## 疲劳检测

出现以下任一信号时，降低问题密度：

- 用户连续两次只回复"嗯""都可以""不知道""你看着办"。
- 用户回答明显变短，或反复要求"直接做"。
- 已经连续 3~4 轮做选择，但核心目标没有发生变化。
- 用户开始重复前面已经说过的内容。

处理顺序：

1. 停止新增非必要问题。
2. 用当前信息定稿草案（未确认项转假设）。
3. 展示"已确认 / 默认假设 / 需要你确认"的简表。
4. 给出"确认方案，开始制作""修改一项""继续梳理"三个入口。

## 退出梳理

以下指令在任何阶段都立即生效：

- 停止梳理
- 直接出方案
- 按目前信息继续
- 按你的推荐来
- 先给我初版

退出时不要声称所有细节都已确认。缺口按 draft-plan.md 转为（假设），并保留确认门。

## 问题预算（唯一口径）

- 问题数量完全动态，**硬上限 5 问**：初始描述越完整问得越少，0 问直接出方案也正常；问满 5 问立即收敛定稿。
- 深挖状态：上限放宽到 10 问，达到即定稿。
- 只有"需要用户做决定的问题"计数；复述、事例邀请、附件检查、记分板小结不计。
- 覆盖度满足完成标准时提前结束，不凑问题数。
