# 版本存档规则（本地版本管理，用户无感）

## 定位

给用户的工具做**本地版本存档**：每次工具做好或改好、用户表示满意后，问一次"要不要存档这一版"。底层用 git（几乎总是现成的），没有 git 时降级为文件夹快照——**两条路用户看到的话术完全一致**，用户永远不接触 git 概念、版本号、备注都由教练代劳。

这是本地存档，与"上传星火平台"是两件独立的事：存档不触发上传；顺序上先问存档、再按需问上传（见 [platform-sync.md](platform-sync.md)、[delivery-template.md](delivery-template.md)）。

## 三条铁律

1. **用户无感**：全程不出现 git、commit、tag、仓库、分支等技术词；用户只看到"存档 / 版本号 / 备注 / 退回"。
2. **备注教练写**：版本备注由教练根据这一版实际改动自动生成，用户一个字都不用填。
3. **每次满意后必问**：首次交付试用通过、以及之后每次修改试用通过，都问一次存档，不打断制作过程。

## 触发时机

试用与微调闭环中，用户明确表示满意（"满意""没问题""可以了"）之后，**先问存档，再按需问上传**：

```text
用户回「满意」
   → ① 问存档（本文件）
   → ② 按需问上传/同步平台（platform-sync.md）
   → 收尾消息（delivery-template.md）
```

不在制作中途、也不在用户还没试用满意时问存档。

## 版本号规则

- **整数递增**：首个存档 = **v1.0**，之后每存一版 +1.0（v2.0、v3.0…）。不区分大改小修，越简单越好。
- 版本号由教练分配，用户不用记，也不用输入。

## 备注规则（教练自动写）

根据这一版实际改动，用固定前缀分类，一版可有多条：

| 前缀 | 含义 |
| --- | --- |
| 🆕 | 首个版本的核心能力 |
| ➕ | 新增功能 |
| 🐛 | 修复问题 |
| ♻️ | 优化体验、性能、文案 |

备注要说人话、指向用户能感知的变化（"对比表新增环比列"），不写技术实现细节。

## 用户话术

### 问存档卡（每次满意后）

首次（v1.0）：

```markdown
🗄️ **要不要帮你把这一版存档一下？**

存档就是给现在这个能用的版本拍个"快照"，以后不管怎么改坏了，一句话就能退回来。

- **A.** 存一下，叫它 **v1.0**　⭐ 推荐
- **B.** 先不用

💡 **推荐 A**：刚验收通过、最干净的状态，最值得存。

*如果以上选项都不符合，可以直接输入你自己的想法。*
```

后续版本（把 v1.0 换成 vN，首句换成"这次的改动要存成新版本吗？"，去掉"最干净的状态"那句理由）。

### 存档成功展示

```markdown
✅ **已存档 · v1.0**　`2026-07-28 16:40`

本版包含：
- 🆕 首个可用版本：多店铺 CSV 合并成横向对比表，支持导出
- 🆕 自动识别销售额/订单数/客单价列，列名对不上的文件自动跳过并提示

📌 以后想回到这一版，直接跟我说「**退回 v1.0**」就行。
```

第 2 版起，成功展示后追加一张版本存档表（当前版标"← 当前"）：

```markdown
📚 **你的版本存档**

| 版本 | 时间 | 说明 |
|---|---|---|
| **v2.0** ← 当前 | 07-28 17:15 | 新增环比列；修复客单价 |
| v1.0 | 07-28 16:40 | 首个可用版本 |

📌 想回到任意一版，跟我说「**退回 v1.0**」这样就行。
```

### 用户回"先不用"

```markdown
好的，这版先不存档。改到你觉得值得留一版时，随时跟我说「**存一下**」就行。
```

### 用户说"退回 vN"

```markdown
⏪ **已帮你退回 v1.0**（07-28 16:40 那一版）。

现在工具就是当时的样子了——环比列已经没有了。
放心，**v2.0 并没有丢**，你随时可以说「退回 v2.0」再回到新版本。
```

退回后当前版本指针指向 vN，但更高版本一律保留、可再退回过去。

## PLACEHOLDER_UNDERLYING

## 底层执行（静默，用户永远看不到）

存档的一切技术动作都不产生面向用户的输出，用户只看到上面的话术。执行前先做两步检测：

```text
1. git 程序装了吗？（which git / git --version）
     没装 → 走「文件夹快照」兜底，结束（不自动安装 git：装 git 在各平台都要弹窗/权限/大下载，反而破坏无感）
     装了 ↓
2. 当前工具目录里有 .git 吗？
     有   → 直接在现成仓库里提交
     没有 → 先 git init 建一个（懒加载，仅首次存档时），再提交
```

绝大多数运行 Claude Code / Codex 的机器都已装 git，git 路径是主线；快照只是 <5% 的兜底。**任何情况下都不主动安装 git。**

### git 路径

首次存档（目录还不是仓库）：

```bash
cd "<工具目录>"
git init -q
printf '样例数据/\n*.tmp\n.DS_Store\nnode_modules/\n' > .gitignore   # 排除样例数据与临时文件
git add -A
git commit -q -m "v1.0 首个可用版本：<一句话备注>"
git tag v1.0
```

后续存档（已是仓库）：跳过 init，直接 `git add -A && git commit -m "vN …" && git tag vN`。

**目录已是"别人的"仓库时**（造工具前这个目录就有 .git，属于用户已有项目）：不新建、不污染，只提交工具自己的文件——`git add "<工具子目录>"`，commit 信息带工具名前缀（如 `[销售对比工具] v1.0 …`），tag 用 `工具名-v1.0` 避免与用户已有 tag 冲突。

**退回**：`git checkout vN -- .`（把工作区还原到该版本，保留更高版本的 tag，不丢历史）。

### 文件夹快照路径（没装 git 时的兜底）

- 存档：把工具目录复制为 `<工具名>_存档/vN/`（排除样例数据/临时文件）。
- 版本表：从 `<工具名>_存档/` 下的子文件夹枚举得出。
- 退回 vN：用 `<工具名>_存档/vN/` 覆盖回工具目录（覆盖前先把当前状态另存为最高版本快照，防止误丢）。
- 用户看到的话术与 git 路径完全相同。

### 时间戳

存档成功展示里的时间取系统当前时间，格式 `YYYY-MM-DD HH:mm`（表格里可简写 `MM-DD HH:mm`）。

## 与平台上传的关系

- 存档是纯本地动作，**不触发**任何上传。
- 存档问完之后，才按 [platform-sync.md](platform-sync.md) 处理上传/同步：
  - 工具**从未上传过** → 走"是否上传星火平台"询问。
  - 工具**曾上传过**（草稿版本记录里有"平台工具：tool-…"）→ 走 platform-sync.md 的"迭代后的版本同步"提醒。

## 写回草稿

每次存档成功后，按 [draft-plan.md](draft-plan.md) 在草稿「版本记录」追加一行：

```markdown
- 存档：v1.0（git tag / 文件夹快照）@ 2026-07-28 16:40 — 🆕 首个可用版本
```

## 失败处理

- git init 或 commit 失败：静默降级为文件夹快照，用户话术不变。
- 快照复制也失败（磁盘满、无写权限等）：如实一句话告知"这版暂时没存上（原因），工具本身不受影响"，不阻塞收尾。
