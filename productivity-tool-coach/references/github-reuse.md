# GitHub 现成方案检索与二次开发评估

## 目标

在决定从零制作之前，先判断是否存在可以直接使用、二次开发或参考借鉴的开源项目。这个环节的目标不是收集最多链接，而是帮助用户做出采用决策。

## 触发条件

仅在以下情况触发：

- 用户的目标、使用者和核心输入输出已经明确。
- 任务可能由现有脚本、应用、库、Skill、模板或工作流覆盖。
- 搜索结果有可能改变实现路线。

不触发的情况：

- 用户明确要求从零制作。
- 需求高度内部定制，公开项目几乎不可能复用。
- 工具非常简单，搜索成本明显高于直接实现。
- 用户明确要求跳过检索。

## 用户选择提示

```markdown
🔍 目前我已经了解到，你想做的是一个"[工具或任务名称]"。

在开始从零设计之前，我可以先帮你联网搜索 GitHub，看看是否已经有类似的开源工具，避免重复开发。

**要先搜一下吗？**

- **A.** 先搜索 GitHub 上的现成工具　⭐ 推荐
- **B.** 只做快速搜索
- **C.** 不搜索，直接从零设计

💡 **推荐 A**：先检查是否存在可复用的基础项目，有机会减少开发工作量，也可能找到更成熟的处理方式。

*如果以上选项都不符合，可以直接输入你自己的想法。*
```

## 搜索策略

优先使用已连接的 GitHub 能力。如果当前环境没有仓库搜索接口，使用网页搜索并限定 GitHub.com 结果。

搜索词应覆盖用户语言和技术语言。例如用户说"CSV批量刷图"，可以组合：

- `csv batch image generation`
- `csv image templating`
- `bulk image generation csv`
- `data driven image generation`
- `batch image processing csv`

不要只使用一个关键词。根据用户的输入格式、输出格式、图片处理方式和运行环境，至少组合2到4组搜索词。

## 候选项目筛选

优先保留2到5个候选项目。每个候选项目至少检查：

- 项目名称、简介和仓库地址
- README中的核心能力和运行方式
- 输入输出是否与用户需求匹配
- 最近维护信号，例如近期提交、发布或活跃讨论
- 开源许可证
- 技术栈、依赖和运行环境
- 是否有可复用的模块、命令或接口
- 二次开发需要修改的范围

如果某项信息无法确认，写"未确认"，不要根据仓库星标或名称推断项目质量。

## 适配度评估

适配度使用高、中、低三个等级，并说明理由：

- 高：核心流程和输入输出基本一致，只需少量配置或局部修改。
- 中：能复用基础能力，但需要补充关键流程、界面或数据适配。
- 低：只有部分能力相关，重构成本接近从零制作。

建议同时给出一个0到5分的辅助分数，但不要只用分数替代解释：

| 维度 | 0分 | 5分 |
| --- | --- | --- |
| 核心功能覆盖 | 完全不覆盖 | 几乎完整覆盖 |
| 输入输出匹配 | 不匹配 | 完全匹配 |
| 运行环境匹配 | 无法运行 | 可直接运行 |
| 可扩展性 | 难以修改 | 有清晰接口或模块 |
| 维护和文档 | 停止维护且资料少 | 持续维护且文档清楚 |
| 许可证可接受性 | 不明确或不符合 | 明确且符合使用目的 |

## 二次开发难度

- 低：配置、模板、少量脚本修改即可。
- 中：需要修改核心流程、增加接口或增加用户界面。
- 高：需要重构核心架构、替换依赖或补齐大量缺失功能。

## 采用建议

对每个项目给出以下之一：

- 直接使用：现有能力已经足够，改动很少。
- 建议二开：基础能力匹配，修改成本明显低于从零制作。
- 参考借鉴：可以学习流程或模块，但不适合作为直接基础。
- 不建议采用：适配度低、维护风险高、许可证不清楚或改造成本过高。

## 最终决策

检索结果展示后，让用户选择：

```markdown

- **A.** 采用最适合的现成项目
- **B.** 基于推荐项目二次开发
```

## 规则边界

- 不把星标数、搜索排名或项目名称当成适配度结论。
- 不把"能运行"直接等同于"适合二开"。
- 不建议用户在没有确认许可证的情况下直接复制代码用于商业项目。
- 不下载、运行或引入陌生仓库中的代码，除非用户已经确认采用该项目并且当前任务进入正式制作阶段。
- GitHub 检索结果只影响实现路线，不替代用户对目标、范围和风险的确认。
