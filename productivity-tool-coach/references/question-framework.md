# 澄清问题框架与覆盖度记分板

## 使用原则

澄清不是把问题问一遍，而是把方案草稿上的 `[待确认]` 一格格填掉。每个问题都要能指出"它填草稿哪一栏"；指不出落点的问题不要问。

每轮只问一个独立问题。能用工作区、附件、真实事例或上下文确认的内容不问用户，直接写入草稿（必要时标假设）。只收集偏好、不影响第一版的问题，记入草稿"后续可扩展"，不问。

## 提问纪律：过去事实优先

凡是能问"上次是怎么做的"，就不问"你希望怎样"。人对过去具体事件的复述基本可靠，对未来偏好的自述基本不可靠。

- 差的问法：你希望工具输出什么格式？
- 好的问法：上次做完这件事，你最后交出去的是什么？发给了谁？

假设性问题只允许用于过去事实覆盖不到的决策：第一版范围取舍、尚未发生的分享方式、新增能力的选择。

## 覆盖度记分板

九个维度与草稿第 1~9 节一一对应。每项三态：

- **清晰**：有用户事实或明确回答支撑，教练能据此直接实现。
- **部分**：有方向，但存在会影响实现的歧义。
- **缺失**：完全没有信息。

| # | 维度 | 判定为"清晰"至少需要 |
| --- | --- | --- |
| 1 | 目标 | 知道要解决哪件事、做好后哪一步明显变快 |
| 2 | 使用者与场景 | 谁用、多久用一次、在什么环境用；期望使用范围（自用/团队/全公司）与同样做这件事的人数 |
| 3 | 现状流程与痛点 | 有真实事例支撑的现状步骤和最痛的一步 |
| 4 | 输入 | 内容、格式、来源（最好有样例文件） |
| 5 | 输出 | 内容、格式、去向 |
| 6 | 操作流程 | 用户怎么开始、哪步要确认、怎么结束 |
| 7 | 第一版范围与实现形式 | 必做/暂不做清单，实现形式候选收敛到一个 |
| 8 | 数据、平台与分享约束 | 敏感性、运行平台、分享对象是否用得起来 |
| 9 | 验收标准 | 至少 2 条"当…时，工具应…"且各配例子 |

记分板只在小结时展示，平时不刷屏。

## 选题算法

每轮提问前依次执行：

1. 列出所有"缺失/部分"的维度。
2. 过滤：只保留答案会改变第一版做法的。
3. 先自答：能用事例、附件或工作区推断的，直接写入草稿标（假设），从清单移除。
4. 剩余按"影响度 × 不确定性"排序（影响度 = 不同答案导致的实现差异有多大）。
5. 取最高一项生成单问题，标题行标注序号和落点：`✍️ **第 3 问 · 填「输出」一栏**`。
6. 清单为空 → 停止提问，进入定稿。

草稿首次落盘时先做一次整体评估：覆盖度已达 7/9 及以上 → 立即告诉用户"你的描述已经很完整，只剩 N 个问题"（N 为剩余核心缺口数，可能为 0）。把"说得清楚 = 问得少"变成用户看得见的正反馈。

## 问题预算

- 问题数量**完全动态，硬上限 5 问**：初始描述和事例覆盖得越多，问得越少；草稿一落盘覆盖度就达标时，0 问直接进入定稿也完全正常。
- 因为上限只有 5，每个问题都必须值回票价：只问会改变第一版做法的核心缺口，按"影响度 × 不确定性"取最高的一个；纯偏好、不阻塞第一版的内容一律用默认值加（假设）解决，不消耗问题额度。
- 计数口径：只有"需要用户做决定的问题"计数；复述、事例邀请、附件检查、记分板小结不计。
- 深挖开关：出现多人使用、权限、外部系统对接、合规信号时，主动建议"这里涉及 X，值得多确认两轮，要吗？"；用户也可随时说"深入一点"。深挖状态下上限放宽到 10 问，达到即定稿。
- 覆盖度已满足完成标准（见 SKILL.md）时提前结束，不凑问题数。

## 各维度问题库

### 1 目标

- 你最想解决哪一件重复、耗时或容易出错的事情？
- 如果这个工具做好了，你希望哪一步明显变快？
- 这个问题多久发生一次？上次发生是什么时候？

### 2 使用者与场景

- 主要由谁使用？只有你自己，还是有同事一起用？
- 这个工具做好后是你自己用，还是团队/更多同事也会用？团队里大概几个人也在做这件事？
- 使用者的技术熟练度如何？
- 通常在哪个设备或工作环境中使用？

### 3 现状流程与痛点

- 上次做这件事，你是从哪一步开始的？中间经过哪几步？
- 哪一步最耗时间？哪一步最容易出错？
- 现在用了哪些文件、工具或平台？

### 4 输入

- 上次的原始材料是什么？能把它（脱敏后）发给我吗？
- 输入来自文件、表格、网页、消息，还是别人发给你的东西？
- 每次输入的格式固定吗？上次和上上次一样吗？

### 5 输出

- 上次做完，你最后交出去的是什么？发给了谁？
- 输出是文本、表格、文件、页面，还是一个动作？
- 你需要先预览确认，还是直接要结果？

### 6 操作流程

- 你打开工具后第一步想做什么？
- 哪一步必须由你确认？哪些可以自动完成？
- 失败或数据不完整时，你想看到什么？

### 7 第一版范围与实现形式

- 第一版必须完成哪一个核心任务？
- 哪些功能可以明确放到后续版本？
- 你更重视尽快可用，还是一次做得更完整？

实现形式由教练根据输入、输出和使用环境提出候选，不直接问用户"要脚本还是网页"——除非两个候选都合理且使用体验差异大，才作为选择题给出。候选排序遵循简单高效优先：同等满足需求时，带图形界面、可双击打开、零依赖的形式排在前面。

### 8 数据、平台与分享约束

- 数据里有没有不能外传的信息？
- 必须在某个平台或某台电脑上运行吗？需要离线吗？
- 要分享给别人用吗？对方能安装依赖或访问部署地址吗？

### 9 验收标准

- 上次做完，你是怎么检查结果没问题的？
- 用哪个例子来验收最有说服力？（优先用用户上传的真实样例）
- 哪些错误必须被明确提示？

### 特殊分支：是否检索现成方案

目标和核心输入输出基本清晰、且任务可能被现有开源项目覆盖时，按 [github-reuse.md](github-reuse.md) 的触发条件询问是否检索。不在开场出现，也不对用户明确要求从零制作的任务重复提出。

## 选择题生成规则

每个问题通常生成 2~3 个基于上下文的选项，只有确实有 4 个互斥且都合理的方向时才提供第 4 个。选项用用户自己的业务词，不用"方案A、方案B"这种空泛标签，也不要重复展示与当前场景无关的通用选项。

固定结构（视觉规范见 [low-burden-conversation.md](low-burden-conversation.md)）：

1. 标题行：`✍️ **第 N 问 · 填「××」一栏**`（N 为计数问题的序号，让用户感知进度）
2. 问题正文
3. 选项：每项单独一行 `- **A.** 选项内容`，推荐项放第一位并在行尾加 `　⭐ 推荐`
4. 推荐行：`💡 **推荐 A**：一句话理由`
5. 固定结尾（斜体）：`*如果以上选项都不符合，可以直接输入你自己的想法。*`

完整示例：

```markdown
✍️ **第 3 问 · 填「输出」一栏**

上一次实际整理时，最花时间或最容易出错的是哪一步？

- **A.** 把链接、时间、负面类型和总结逐项填进 CSV　⭐ 推荐
- **B.** 在搜索结果里找相关内容、判断是否算负面评价
- **C.** 两步都差不多

💡 **推荐 A**：这一步字段明确、重复度高，最适合第一版先自动化。

*如果以上选项都不符合，可以直接输入你自己的想法。*
```

运行环境提供原生提问/选项控件时（如 Claude Code 的 AskUserQuestion），优先用控件呈现选择题，选项内容与文字模板等价；否则用 markdown 模板。

## 不知道时的处理

用户说"不知道""都可以""随便""你决定""暂时跳过"时：

1. 用一句话说明这个决定会影响什么。
2. 给一个适合第一版的默认方案，写回草稿并标（假设）。
3. 允许用户直接回复"按推荐继续"。
4. 这个决定不阻塞第一版时，不再追问，推进下一个真正影响制作的问题。

不要把"不知道"变成连续追问。
