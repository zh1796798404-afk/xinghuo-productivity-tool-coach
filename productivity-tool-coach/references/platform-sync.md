# 星火平台数据回传与工具上传

## 定位与三原则

教练在制作过程中自然采集的信息，静默回传到星火平台的数据表（工具制作过程表 build_session）；工具做好且用户满意后，经用户明确同意再把成品上传回平台（工具表 tool + 平台文件存储）。遵循平台 PRD 的三条原则：

- **自动优先**：所有回传字段都来自草稿、事例提取和运行环境，不为数据采集单独提问。唯一的新增信息点（期望使用者、涉及人数）已并入九维记分板第 2 维，由正常选题算法决定问不问。
- **静默同步**：回传动作不在聊天里刷存在感；失败不打扰用户、不阻塞任何主流程。
- **知情**：草稿首次落盘的消息末尾用一行话告知（仅一次）：

```text
📡 过程数据会同步到星火平台的制作记录（仅目标、频率、耗时等元数据，不含你的任何文件内容）。
```

## 启用条件（配置发现）

尝试读取 `~/.spark-coach/config.json`：

```json
{
  "platform_upload_url": "http://localhost:8788/api/upload",
  "base_token": "<多维表格 base_token>",
  "build_table_id": "<build_session 表 table_id>",
  "tool_table_id": "<tool 表 table_id>",
  "user_name": "<姓名，可空：运行时自动获取>",
  "user_open_id": "<open_id，可空：运行时自动获取>",
  "user_department": "<部门，建议填写>"
}
```

**身份获取顺序**：姓名和 open_id 优先在首次同步时自动获取——`lark-cli contact +get-user --as user`（返回 `data.user.name` 和 `data.user.open_id`），config 中的同名值仅作覆盖；部门信息 basic_profile scope 拿不到，取 config 值（生产态由平台的飞书认证下发，不走插件）。

以下任一情况 → **平台同步整体禁用**，草稿版本记录写一行"平台同步：未启用"，其余流程完全不变，不向用户解释技术细节：

- 配置文件不存在或非法
- `lark-cli` 不在 PATH
- 首次写入时鉴权失败

## build_session 记录生命周期

### 创建（草稿 v0 落盘后立即执行一次）

制作记录 ID 格式：`bs-YYYYMMDD-HHMMSS`。已验证的命令形状：

```bash
lark-cli base +record-upsert --base-token "<base_token>" --table-id "<build_table_id>" --as user \
  --json '{
    "制作记录ID": "bs-20260717-101500",
    "制作人": "<user_name>",
    "制作人open_id": "<user_open_id>",
    "所在部门": "<user_department>",
    "开始时间": "2026-07-17 10:15:00",
    "痛点描述": "<草稿第1、3节摘要，一两句>",
    "痛点场景分类": "数据处理",
    "搭建结果": "进行中",
    "模型与环境": "<Codex/Claude Code + 模型档位，能感知多少写多少>"
  }' --jq '[.. | strings | select(startswith("rec"))] | first'
```

命令输出即 `record_id`（`rec` 开头）。把两个 ID 写入草稿「版本记录」：

```markdown
- 平台同步：bs-20260717-101500 / recXXXXXXXX
```

### 字段映射（草稿 → build_session）

| 表字段 | 来源 | 写入时机 |
| --- | --- | --- |
| 制作记录ID / 制作人 / open_id / 所在部门 / 开始时间 | config + 系统时间 | 创建时 |
| 痛点描述 | 草稿第 1、3 节摘要 | 创建时，草稿修正后跟随更新 |
| 痛点场景分类 | 教练按枚举归类：数据处理 / 文件批处理 / 内容生成 / 流程审批 / 信息检索 / 其他 | 创建时 |
| 痛点频率 | 事例提取（如"每周1次"） | 落草稿后 |
| 单次耗时分钟 | 事例提取，换算成分钟数字 | 落草稿后 |
| 涉及人数 / 期望使用者 | 九维第 2 维（自用 / 团队用 / 全公司用） | 该维清晰后 |
| 工具类型 | 实现形式确定后按枚举：Skill / 脚本 / 网页应用 / 桌面程序 / 表格模板 / 其他 | 确认门通过时 |
| 澄清问答轮数 | 计数问题总数 | 确认门通过时 |
| 附件样例数 | 用户上传的真实样例个数 | 确认门通过时 |
| 验收通过数 / 验收总数 | 验收核对表结果 | 核对完成时 |
| 迭代轮数 | 试用闭环中的微调次数 | 试用闭环结束时 |
| 完成时间 / 搭建结果 | 系统时间；成功 / 放弃 / 转提单 | 试用闭环结束或用户中止时 |
| 是否上传回流 / 关联工具ID | 上传流程 | 上传完成时 |

### 更新命令（已验证形状）

```bash
lark-cli base +record-upsert --base-token "<base_token>" --table-id "<build_table_id>" \
  --record-id "<recXXXX>" --as user \
  --json '{"痛点频率":"每周1次","单次耗时分钟":60,"涉及人数":3,"期望使用者":"自用"}' --jq '.ok'
```

### 数据保真规则（宁缺勿假）

- 痛点频率、单次耗时、涉及人数三个统计字段直接进提效工时公式，**只同步用户亲口提供的值**（描述、事例或回答中出现过）；用户没给、只有（假设）标记的值一律留空不入库。
- 痛点场景分类、工具类型两个枚举字段由教练按枚举归类，不问用户（用户对枚举无概念，归错代价低）。
- 其余字段均为系统事实（轮数、时间、验收结果等）或飞书身份，不存在推测空间。

### 命令拼装注意

- `--json` 与 `--jq` 的外层统一用单引号包裹；JSON 值里不要出现未转义的单引号或反引号。
- 需要在 shell 变量里拼 JSON 时，先把 JSON 写成临时字符串再传入，避免多层引号嵌套出错。

### 同步节奏

- 与草稿原子写回同拍：每次写回后，若映射字段有变化，追加一次静默更新；无变化不调用。
- 数字字段必须传 JSON number（60，不是 "60分钟"）；单选传选项名字符串；时间传 `YYYY-MM-DD HH:mm:ss`。
- 用户中途说放弃 → 搭建结果=放弃；转提单 → 搭建结果=转提单，均写完成时间。

### 失败处理

- 任何一次同步失败：静默跳过，草稿版本记录标"平台同步：暂不可用（最后成功：第 N 问后）"；下一次写回时重试一次。
- 只在试用闭环收尾时，如同步仍失败，用一句话向用户提及（"制作记录暂时没同步上平台，不影响工具使用"）。

## 工具上传（试用闭环用户表示满意、并处理完本地存档之后）

### 询问（存档之后问上传，上传之后才发收尾消息）

```markdown
🚀 **最后一件事：要把这个工具上传到星火平台吗？**

上传后经审核就会出现在工具市场，其他遇到同样麻烦的同事能直接拿去用——你也会成为平台共建者。
🎁 **限时激励：前 100 名上传工具的同事，每个上架工具奖励 20 Bold 币！**

- **A.** 上传到星火平台　⭐ 推荐
- **B.** 暂不上传，先自己用

💡 **推荐 A**：工具已通过你的亲手验收，正是分享的最佳状态；上传只要几秒钟。

*如果以上选项都不符合，可以直接输入你自己的想法。*
```

> 🎁 激励行是**运营活动文案**：活动规则调整或结束时同步更新/删除这一行（选 B 回应里的钩子同理），其余文案不动。

### 用户选 A：上传步骤

1. **打包**：把工具目录压缩为 zip（`zip -r -X 工具名.zip 目录 -x "*.DS_Store"`）。**打包前检查并剔除用户的真实样例数据**——包里只留工具本体和说明。
2. **上传**（已验证形状）：

```bash
curl -s -m 300 -F "file=@工具名.zip" "<platform_upload_url>"
```

返回 JSON 取 `.result.data.url`（形如 `https://xxx.feishu.cn/file/<token>`）作为下载链接。

3. **登记 tool 表**（已验证形状；工具 ID 格式 `tool-YYYYMMDD-HHMMSS`）：

```bash
lark-cli base +record-upsert --base-token "<base_token>" --table-id "<tool_table_id>" --as user \
  --json '{
    "工具ID": "tool-20260717-113000",
    "工具名称": "<草稿工具名>",
    "工具类型": "<枚举>",
    "工具描述": "<草稿第1节：解决什么痛点、适用场景>",
    "使用方法": "<分步手册的前几步摘要 + 安装要点>",
    "标签": "<业务场景标签，逗号分隔>",
    "运行环境要求": "<是否需要 agent 环境、依赖说明；零依赖就写零依赖>",
    "发布人": "<user_name>",
    "发布人open_id": "<user_open_id>",
    "所在部门": "<user_department>",
    "下载链接": "<上一步的 url>",
    "来源渠道": "教练制作回流",
    "关联制作记录ID": "<bs-…>",
    "提交时间": "<当前时间>",
    "审核状态": "待审核"
  }' --jq '[.. | strings | select(startswith("rec"))] | first'
```

命令输出即 tool 记录的 `record_id`（下一步写双向关联要用）。

> 上传模式（存量工具，见 [upload-mode.md](upload-mode.md)）走同一条登记命令，仅两处不同：`来源渠道` 写 `存量工具插件上传`，且不写 `关联制作记录ID`、不做第 4 步回写。

4. **回写 build_session**（含双向关联，两表可点击跳转；tool 表侧会自动出现「关联制作记录」反向链接）：

```bash
lark-cli base +record-upsert --base-token "<base_token>" --table-id "<build_table_id>" \
  --record-id "<制作记录的 recXXXX>" --as user \
  --json '{"是否上传回流":true,"关联工具ID":"tool-…","搭建结果":"成功","完成时间":"<当前时间>","关联工具":[{"id":"<tool 记录的 record_id>"}]}' --jq '.ok'
```
5. **登记到草稿**：在草稿「版本记录」追加一行（record_id 供以后版本同步用）：

```markdown
- 平台工具：tool-20260717-113000 / recXXXXXXXX
```

6. **告知用户**：

```markdown
✅ **已上传星火平台**（审核通过后会出现在工具市场）
🔗 下载直链：<url>
📦 本地包：<zip 路径>（也可以直接发给同事）
```

### 用户选 B

- build_session：`是否上传回流=false`、`搭建结果=成功`、`完成时间`（自用工具同样计入提效统计）。
- 回复一句"好的，工具先归你自己用；以后想分享随时叫我——上架奖励在前 100 名内都有效 😉"，然后正常收尾，不再追问。

### 上传失败

一句话告知 + 给出本地 zip 路径 + "稍后可以再传"，不影响交付收尾；build_session 标 `是否上传回流=false`。

## 迭代后的版本同步（工具曾上传平台时必做）

触发：迭代短流程或后续微调中，用户对修改表示满意，**且**草稿版本记录里有「平台工具：tool-… / rec…」（说明平台上挂着旧版本）。此时必须提醒，不能让平台上的版本悄悄落后：

```markdown
🔄 **平台上挂的还是旧版本**——要把这次更新同步上去吗？

- **A.** 同步新版本到星火平台　⭐ 推荐（用你工具的同事才能拿到修复）
- **B.** 暂不同步

*如果以上选项都不符合，可以直接输入你自己的想法。*
```

用户选 A：

1. 重新打包 zip（同样剔除用户样例数据）→ 上传平台取新直链。
2. 更新工具表原记录（用版本记录里的 rec ID）：

```bash
lark-cli base +record-upsert --base-token "<base_token>" --table-id "<tool_table_id>" \
  --record-id "<平台工具的 recXXXX>" --as user \
  --json '{"下载链接":"<新 url>","提交时间":"<当前时间>","审核状态":"待审核","工具描述":"<原描述>（vN 更新：一句话说明本次改动）"}' --jq '.ok'
```

3. 告知用户：`✅ 新版本已同步星火平台（重新进入审核）　🔗 新直链：…`；草稿版本记录追加一行更新说明。

用户选 B：回复"好的，需要时随时说'同步新版本'"，并在草稿版本记录标"平台版本落后于本地 vN"。

工具**从未上传过**的迭代场景：不走本节，照常走"工具上传"询问（含激励行）。

## 隐私与安全边界

- 回传的只有过程元数据（痛点摘要、频率、耗时、人数、轮数、验收结果、环境信息），**永不包含**用户的业务文件、样例数据内容或聊天原文。
- 工具包上传必须经用户明确选择 A；包内不得含用户真实样例数据。
- 用户询问同步了什么时，如实展示字段清单和表格链接。
